Number Garden Architecture

A maths garden for a five-year-old, built as one HTML page with no server of its own. Everything the child does lives on her device; a public static host serves the page, a public database syncs between devices by family code, and nothing else exists to run or pay for.

Where things live

Three places, one of which is the child's own browser. The page is the whole app. GitHub serves it and tests it; Firestore holds a copy of each family's garden and the bug reports a child files by tapping Tell Pip. The arrow that matters is the one from the device to the database: it carries the garden, never a login.

Why one file

Save and refresh is the whole development loop, there is one thing to publish, and the page drops into any static host. The source is split into 39 files for people; a shell script concatenates them byte for byte and a check fails the build if the page drifts from its sources.

Why no server

A static host costs nothing and cannot leak what it does not have. The Firestore web key is public by design; the published rules are the access control: one nine-character code reads and writes one garden document, reports are create-only, everything else is closed.

Inside the page

Five layers, calls going down and events coming back up. Games know nothing about screens, storage or the network; they describe a problem and the engine does the rest, which is what lets 67 games share one thinking loop.

The game contract

skill({id, room, title, levels, teach(lv, L), mount(lv)}) registers a game. Inside mount it draws into the stage, puts inputs in the controls and calls help({book, clues, answer, why, show, guess, reasons, ways}). It reports with win() or miss(). That is the whole surface.

What the engine adds

Levels that climb after three clean answers and drop after two heavily hinted ones, never shown to the child. A lesson once per level. A think-first guess, a why gate on odd problems and an another-way gate on even ones, the own-words card, the museum of slips, Pip's moods and voice.

One trail, start to finish

What happens between a tap on a door and a new flower. The child meets five problems; each one goes through the same loop, and the state is saved and synced after every stone, so closing the tablet mid-trail loses nothing.

From an edit to the child's screen

Nothing reaches the live site without passing the same checks twice: once on the machine that made the change, in a fast mode that shrinks every animation and lesson pause, and once on GitHub, split into 6 parallel jobs so a push is fully checked in a few minutes.

  • Smoke mounts all 190 game levels and taps Clue and Show me on each; books walks every page of all 32 picture books; trails builds five-stone trails from every door; sync simulates two devices against a mocked Firestore; 52 solve scripts play each game clean and miss-then-recover.
  • Browsers run one at a time on a single machine, behind a lock, because two at once crash the sandbox. CI has 6 machines, each running a deterministic slice of the list.

Principles the structure protects

Nothing of the child in the repository

The default name is Sprout, pronouns are a setting, and the public repository holds no names, codes or reports. Her garden exists on her device and, by family code, in one Firestore document.

No clocks, no X marks

A miss gives a hint about the structure of the problem. Levels adapt silently. The daily limit counts quietly and closes the garden at the next stone, never mid-problem.

Teach before asking

Every game carries a lesson Pip shows once per level before the first problem, and a Big Idea book behind the Learn button. Asking first would be unfair.

Explaining is not tied to being wrong

Why gates, another-way gates, think-first guesses and the own-words card ask the child to reason on right answers too, so a correct number is the start of the thinking, not the end.
